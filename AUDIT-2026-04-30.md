### 🟡 MEDIUM (4)

#### M1. Markdown link injection vía `tether_quote.url` y `citation.details.url`
**File**: [src/formatters/chatgpt-markdown.ts:256](src/formatters/chatgpt-markdown.ts#L256), [src/formatters/claudeai-markdown.ts:170-171](src/formatters/claudeai-markdown.ts#L170-L171)

`renderTetherCitation` interpola el `url` del modelo directamente dentro de un markdown link `[title](URL)` sin validar el esquema ni escapar paréntesis. Si la respuesta de ChatGPT/Anthropic incluye un `url: "javascript:alert(1)"` o `url: "http://x.com/) malicious-text ["`, lo emitido al `.md` rompe el link y/o crea uno con esquema arbitrario.

```ts
lines.push(`> 🔗 [${maybeRedact(title)}](${url})`);   // chatgpt-markdown
ctx.footnotes.push(`[^${String(index)}]: ${url}`);    // claudeai-markdown
```

**Vector de ataque**: el modelo (o un atacante que sembró contenido en una conversación compartida) inyecta una URL con esquema `javascript:` / `data:`. Cuando el usuario abre el `.md` en VS Code la mayoría de los renderers de markdown desactivan `javascript:`, pero **otros consumidores** (browsers donde el usuario suba el `.md` a un wiki, GitHub render con `data:`, herramientas que reenvían a Slack, etc.) pueden ejecutarlo.

**Por qué importa**: el `.md` se auto-attachea a Claude Code como `@-mention`. Un humano clickeando el link sale al renderer del IDE; impacto bajo en VS Code pero alto si exporta para compartir.

**Fix recomendado**: validar esquema (`http`/`https`/`mailto` whitelist) antes de interpolar; si no pasa, renderizar el URL como texto plano dentro de un fence o entre backticks. Escapar paréntesis `(` `)` cerrantes en cualquier caso.

#### M2. Sin Rate Limiting en el HTTP bridge (todos los endpoints)
**File**: [src/extension/http-server.ts](src/extension/http-server.ts)

Ver sección **RATE LIMITING** al final con detalle. Resumen: el bridge no limita requests por IP / por endpoint / por ventana. La defensa actual es Bearer + bind a 127.0.0.1 + Origin guard. Un atacante con un proceso local (otro proceso del mismo usuario, p. ej. malware ya con foothold) puede:

1. Brute-forcear el token (bueno: 256 bits, infactible).
2. **Spamear `/import-inline` con 50 MB de payload** hasta colmar memoria — sin auth válido devuelve 401 rápido, pero el server lee el body **antes** de validar el auth en algunos casos (ver M2.b abajo).
3. Slowloris (M2.c): mantener N conexiones abiertas enviando 1 byte/segundo, ahogando el `http.createServer` default que no tiene `headersTimeout` ni `requestTimeout` configurados.

#### M2.b — Auth check ocurre **después** del Content-Length pero **antes** del body parse
**File**: [src/extension/http-server.ts:234-264](src/extension/http-server.ts#L234-L264)

El orden actual del pipeline en `/import` y `/import-inline` es:
1. Method check (POST).
2. URL check.
3. Auth check (bearer compare).
4. Origin check.
5. Content-Length precheck.
6. `readBody()` (streaming, hasta `maxBytes`).

Esto es correcto — el body se lee solo si el auth pasó. Pero **`/ping` no tiene Content-Length precheck** y, aunque `/ping` no espera body, no abortamos si llega uno. En la práctica `req.on('data')` no se conecta así que el body se descarta, pero no es defense-in-depth: un cliente malicioso puede mandar `/ping` con auth válido y un body gigante; Node lo bufferea internamente. No exploit, pero raro.

**Fix sugerido**: agregar un `req.destroy()` tras el `sendJson(200, {ok})` en `/ping`, o un `Content-Length: 0` enforcement.

#### M2.c — `http.createServer` default sin `headersTimeout`/`requestTimeout`
**File**: [src/extension/http-server.ts:166-170](src/extension/http-server.ts#L166-L170)

Node 20+ default es `headersTimeout: 60000` y `requestTimeout: 300000`. Suficiente para no bloquearse forever, pero **5 minutos por request** + N conexiones = N×5min de file descriptors abiertos. Con el bind a 127.0.0.1 el atacante tiene que ser local — riesgo bajo. Pero Slowloris-style es trivial de testear.

**Fix sugerido**: `server.headersTimeout = 5000; server.requestTimeout = 30000; server.keepAliveTimeout = 5000;`. No degrada UX (la Companion siempre cierra rápido) y cierra el agujero.

#### M3. `runTemplate` ejecuta `claude-vscode.*` con cualquier comando registrado
**File**: [src/extension/control-panel.ts:232-265](src/extension/control-panel.ts#L232-L265)

El handler valida que el mensaje tiene `text: string`, lo copia al clipboard y luego ejecuta dos comandos hardcoded (`claude-vscode.sidebar.open`, `claude-vscode.focus`). Está bien — los nombres están hardcoded, no vienen del webview.

**Cross-reference vs el riesgo teórico**: el atacante no controla qué comando se ejecuta, solo controla `text`. Lo único que va a un sink "ejecutivo" es `vscode.env.clipboard.writeText(text)`. Eso es seguro.

**Sub-issue real**: `text` viene del setting `exportal.postImportTemplates` que el usuario edita en `settings.json`. Como ese setting está bajo el control del usuario y se renderiza en una UI propia, no hay cross-trust. Pero `cleaned = templates.filter(t => typeof t === 'string')` no aplica un cap de longitud. Un usuario que copie un template de 10 MB se queda con el clipboard de 10 MB y la UI con un botón de 10 MB — UX bug, no vector de seguridad.

**Recomendación**: cap `t.length > 4000 ? t.slice(0, 4000) : t` (defensa contra accidente). NO un security finding hard, pero por completitud.

#### M4. `sendInline` en Chrome reenvía el conversation entero sin sanitización ni cap
**File**: [chrome/background.js:156-186](chrome/background.js#L156-L186)

El handler `exportal:sendInline` valida que `conversation` es un objeto y filtra `assets`, pero el conversation object completo se reenvía al bridge. Si claude.ai/chatgpt.com son comprometidos (XSS en su propio dominio), el atacante puede inyectar un `conversation` con campos arbitrarios — `__proto__`, prototipos, claves enormes. La defensa real está en el bridge (Zod schema valida la shape).

**Vector teórico**: `JSON.parse` del body del POST en el bridge. Node's JSON.parse NO crea entradas en `__proto__` cuando se usa con object literal — eso es seguro. Zod además filtra (chatgpt schema usa `strip` por default). Claude.ai schema usa `.passthrough()` (S1 del audit anterior, sigue presente).

**Riesgo**: bajo. claude.ai schema con passthrough deja pasar campos arbitrarios al formatter, que los ignora. **No exploitable** porque ningún sink en formatters/* hace `Object.assign(target, parsed)` ni `target[key] = parsed[key]` con keys controladas — siempre se accede por property name conocido (`block.text`, `message.content`, etc.). Confirmado leyendo `claudeai-markdown.ts` y `markdown.ts`.

**Recomendación cosmética**: documentar en el schema que `passthrough` está OK porque ningún consumer enumera las keys.

### 🟢 LOW (5)

#### L1. `fenceCode` no es robusto contra fences de 4+ backticks
**File**: [src/formatters/markdown-shared.ts:77-84](src/formatters/markdown-shared.ts#L77-L84)

```ts
const needsLongFence = trimmed.includes('```');
const fence = needsLongFence ? '````' : '```';
```

Si el contenido del tool_result/code block contiene literalmente cuatro backticks consecutivos `` ```` ``, el fence de 4 backticks lo cierra prematuramente. Vector: una conversación que cite código markdown anidado.

**Impacto**: el bloque "rompe" visualmente y el contenido posterior se renderiza fuera del fence. **No es XSS** — markdown renderers escapan HTML por default — pero sí permite que un atacante (o un mensaje legítimo con backticks raros) saque texto fuera del bloque designado y lo presente como prosa.

**Fix**: contar el run máximo de backticks consecutivos en `trimmed` y usar uno más. Ya es estándar en CommonMark spec.

**File**: [src/extension/extension.ts:494](src/extension/extension.ts#L494), [src/extension/extension.ts:1400](src/extension/extension.ts#L1400)

El único `openExternal` con input dinámico es [control-panel.ts:225-231](src/extension/control-panel.ts#L225-L231) (`openExternal` para docs/changelog) y ahí ya hay whitelist contra `https://github.com/dioniipereyraa/ClaudeTool`. Bien hecho.

#### L3. `consumePairingFragment` lee fragmento de URL pero ya está mitigado
**File**: [chrome/content-script.js:1365-1400](chrome/content-script.js#L1365-L1400)

El comment del propio código admite: "Malicious inbound links (someone else's token) can overwrite the user's pairing but can't exfiltrate data". Confirmado — el bridge en VS Code tiene su propio token y rechaza el mismatched. La única consecuencia es que el siguiente export falla con 401. No es exploit.

**Punto fino**: `extractPairingToken` tolera fragmentos > 64 hex (matchea `^[0-9a-fA-F]{64}$` con anchors). Bien anclado, no hay polyglot.

#### L4. `playSuccessTone` duplicado verbatim en `options.js` y `content-script.js`
**File**: [chrome/options.js:114-138](chrome/options.js#L114-L138), [chrome/content-script.js:1202-1228](chrome/content-script.js#L1202-L1228)

No es seguridad. Es deuda técnica: el mismo array de frecuencias en dos lugares. Si el dev cambia el sonido en uno y olvida el otro, el "Test" del options queda desincronizado del export real. El comment lo admite ("Keep the two in sync if the sound design changes") pero no hay mecanismo que lo asegure.

**Recomendación**: mover a `pure.js` como helper agnóstico (recibe AudioContext factory).

#### L5. Webview en `control-panel.ts` con `style-src 'unsafe-inline'`
**File**: [src/extension/control-panel.ts:472](src/extension/control-panel.ts#L472)

```html
<meta http-equiv="Content-Security-Policy" content="default-src 'none'; img-src ${cspSource} data:; style-src ${cspSource} 'unsafe-inline'; font-src ${cspSource}; script-src 'nonce-${nonce}';">
```

`'unsafe-inline'` en `style-src` permite atributos `style="..."` y `<style>` blocks. Como todo el HTML es generado por el extension (no por user input vía `escapeHtml`), no hay vector. Pero es la diferencia entre "estricto" y "casi estricto". Mover los estilos inline a `<style>` tagueado con nonce sería el upgrade pro forma.

**No fix necesario** (todo el contenido es controlled-by-extension), pero notar que el otro webview (`renderPairingHtml` en extension.ts:527) tiene la misma config. Consistente.

## BUGS

### 🟡 MEDIUM (1)

#### B1. Race condition entre `dismissPostImport` y `notifyPostImportIfReady`
**File**: [src/extension/control-panel.ts:202-206](src/extension/control-panel.ts#L202-L206), [src/extension/extension.ts:71-75](src/extension/extension.ts#L71-L75)

Escenario:
1. Usuario hace export A → llega a `notifyPostImport(A)` → `pendingImportFilename = A`, postMessage al webview.
2. Usuario hace click en X (dismiss) — `dismissPostImport` setea `pendingImportFilename = undefined`.
3. **Entre el postMessage y el click del usuario**, otro export B llega y dispara `notifyPostImport(B)`.
4. El `dismissPostImport` cierra el panel pero `pendingImportFilename` quedó en B (último write-wins).
5. Si el usuario oculta y vuelve a mostrar el panel, **B aparece** aunque acaba de dismissar la sección.

**Probabilidad**: baja en uso humano (dos exports back-to-back es raro), pero observable si el usuario usa el shortcut Alt+Shift+E rápido en dos chats.

**Fix**: en `dismissPostImport`, marcar un flag "user explicitly dismissed for now" y respetarlo hasta el próximo activate(). O versionear cada notify con un counter y solo aceptar dismiss del counter actual.

## RATE LIMITING

**Estado actual**: ninguno.

El bridge HTTP no implementa rate limiting en ninguno de sus 3 endpoints. La defensa actual es:
1. Bind a 127.0.0.1 → solo procesos locales.
2. Bearer token de 256 bits con `timingSafeEqual` → infactible brute-force.
3. Origin guard → rechaza requests de páginas web cross-origin.
4. Body size cap (64 KB / 50 MB) → bounded memory por request.
5. Schema validation con Zod → bounded CPU por request.

**Lo que falta** (en orden de impacto):

### Por-IP rate limit
**Innecesario en el threat model actual**. 127.0.0.1-only — toda IP es la misma. Implementarlo solo agrega complejidad sin beneficio.

### Por-endpoint rate limit con sliding window
**Recomendado**. Un proceso local malicioso puede:
- Spamear `/import-inline` con 50 MB de payload válido → memoria sostenida del extension host.
- Spamear `/ping` con auth válido → CPU del listener (timingSafeEqual).
- Spamear `/import` con paths inválidos → schema validation overhead.

**Recomendación concreta**:
- `/ping`: 30 req/min (la Companion legítima lo hace ~1/min).
- `/import`: 10 req/min (un usuario importa esporádicamente).
- `/import-inline`: 30 req/min (un usuario activo puede exportar 5-10 chats en ráfaga, pero 30 cubre cualquier caso real).

Implementación sugerida: `Map<endpoint, { windowStart: number, count: number }>` global, sliding 60s. Devolver `429 Too Many Requests` con `Retry-After: <seconds>`.

### Slowloris / connection-level limits
**Recomendado** (M2.c arriba). Setear:
- `server.headersTimeout = 5000`
- `server.requestTimeout = 30000`
- `server.keepAliveTimeout = 5000`
- `server.maxHeadersCount = 50`

Estos son cambios de 4 líneas en `listenOnPort`.

### Concurrent connection cap
**Opcional**. Node default es ilimitado. Un atacante local puede abrir N FDs hasta ulimit. Siendo localhost, casi imposible que sea problema real. Pero si querés blindar: contar conexiones activas con `server.on('connection', ...)` y rechazar > 20 simultáneas.
